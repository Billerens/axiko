# Хранение снимков и откат

[English](snapshot-storage.md) · Русский

История хранит одинаковые байты файла один раз независимо от имени и числа снимков.
Рабочая папка остаётся отдельным деревом: её правки не должны менять историю. Это история
кода, а не замена [резервной копии личных данных](backup.md).

## Формат и обязательные свойства

```text
files/history/
  .objects/<первые 2 символа SHA-256>/<остальные 62 символа>
  <snapshot-id>/
    meta.json
    manifest.json
```

`meta.json` содержит ID, время и название. Манифест формата 2 записывает относительные пути,
SHA-256, размеры, исполняемый признак и каталоги. Новые снимки включают обычные файлы любого
поддерживаемого размера и пустые каталоги. Символьные ссылки и специальные файлы отклоняются,
чтобы история не вышла за пределы рабочей папки.

Объекты записываются через временный файл, синхронизацию и переименование. Снимок становится
виден только после готовности объектов и манифеста. Нельзя создавать жёсткие ссылки на
рабочие файлы или менять уже существующий объект. Перед восстановлением проверяется целостность.

## Перенос прежнего формата

При запуске фоновая миграция переводит старые `<id>/files/`; до её окончания прежний формат
остаётся читаемым. Миграция и операции истории сериализованы. `needsMigration()` проверяет
структуру и метаданные вместо полного хеширования при каждом запуске. Ручной `snap.migrate`
по-прежнему выполняет полную проверку.

Сначала записываются объекты и манифест, затем сверяются исходные пути, размеры и хеши.
Только после этого старое дерево переименовывается в `.migrated-files` и удаляется.
Прерванный перенос или очистка продолжаются при следующем запуске. Сама миграция не сокращает
количество снимков.

У старых снимков остаётся `legacyMaxFileBytes`: существующие рабочие файлы больше прежнего
лимита 5 МиБ, которых нет в снимке, переживают откат. Байты, которые никогда не сохранялись,
восстановить нельзя. Если такой файл конфликтует с деревом снимка, откат отклоняется до
изменения рабочей папки.

## Восстановление и хранение

Откат проверяет каждый объект и собирает отдельную папку восстановления. Текущий код тоже
сохраняется снимком для отмены отката, затем каталоги меняются переименованиями. Журнал
`state/restore-transaction.json` восстанавливает прерванную замену до установки заводских
файлов. Личные данные модулей и чаты находятся вне рабочей папки и не откатываются.

Обычное обслуживание оставляет последние 60 снимков. Объект удаляется только тогда, когда
на него больше не ссылаются сохраняемые снимки. Нечитаемый или повреждённый опубликованный
манифест блокирует сборку мусора: нельзя угадывать, какие объекты ему были нужны. Большие
и двоичные файлы нельзя загружать как неограниченный построчный текст для сравнения.

## API и проверки

Нативные операции: `snap.list`, `snap.changes`, `snap.diff`, `snap.restore`, `snap.storage`,
`snap.migrate`. Статистика различает логический размер всех версий, уникальные объекты и
размер файлов истории с манифестами. Выделенные блоки файловой системы измеряются отдельно.

Реализация — [SnapshotStore.kt](../app/src/main/java/app/axiko/core/SnapshotStore.kt) и
[Workspace.kt](../app/src/main/java/app/axiko/core/Workspace.kt). JVM-тесты проверяют общие
байты, неизменность объектов, перенос и продолжение миграции, повреждения, безопасную
очистку, большие файлы, откат старого снимка, его отмену и прерывание замены каталогов.

```powershell
.\gradlew.bat testDebugUnitTest --tests app.axiko.SnapshotStoreTest --tests app.axiko.WorkspaceHistoryTest
```
