## Вывод

Встроенный агент уже способен добавлять функции, выполнять код, открывать экраны, проверять результат и исправлять замеченные ошибки. Для небольшого модуля имеется почти весь набор нужных инструментов.

Надёжность полного цикла пока зависит от того, выберет ли модель правильный порядок действий. Приложение не требует подтверждённой проверки перед завершением, не запускает исправление по результатам автоматических проверок и не всегда различает успех, отсутствие проверки и прерванную работу.

Доработки вроде недавнего исправления вкладок и ускорения каталога находятся в обычной доступной агенту области файлов. Ему доступны необходимые изменения и возможность измерений через JS. Сейчас нет стандартного сценария, который обязательно проверит раскладку вкладок и время появления каталога.

## Главные препятствия

### 1. Автоматическая проверка заканчивается отчётом, а не исправлением

Модель может закончить цикл ответом без инструментов; затем отправляется done. Проверки изменённых модулей выполняются позже, в finally, и сохраняются как отметка в интерфейсе. Они не добавляются в сообщения модели и не запускают следующую попытку. При красных проверках задача всё равно может получить DONE.

Основание: [Conversation.kt:563](D:/Projects/Аксико/app/src/main/java/app/assi/agent/Conversation.kt:563), [Conversation.kt:629](D:/Projects/Аксико/app/src/main/java/app/assi/agent/Conversation.kt:629), [Conversation.kt:643](D:/Projects/Аксико/app/src/main/java/app/assi/agent/Conversation.kt:643), [Conversation.kt:661](D:/Projects/Аксико/app/src/main/java/app/assi/agent/Conversation.kt:661).

**Предложение:** до окончательного завершения вводить этап verify. Провалы возвращать модели с диагностикой, давать ограниченный бюджет исправлений, повторять затронутые проверки. После исчерпания бюджета сохранять результат и причину остановки. Финальный статус должен различать проверенный результат, неудачные проверки, отсутствие проверки, ожидание данных и прерывание.

### 2. Успех инструмента может противоречить его выводу

Tools.run ставит ok=true, если наружу не вышло исключение. Но js_eval перехватывает ошибку и возвращает её текстом; ui_eval так же возвращает ошибку или таймаут; shell/linux помещают ненулевой exit code в строку. Модель может прочитать сообщение, но автоматическая система получает неверный признак успеха.

Основание: [Tools.kt:327](D:/Projects/Аксико/app/src/main/java/app/assi/agent/Tools.kt:327), [Tools.kt:354](D:/Projects/Аксико/app/src/main/java/app/assi/agent/Tools.kt:354), [Tools.kt:398](D:/Projects/Аксико/app/src/main/java/app/assi/agent/Tools.kt:398), [Tools.kt:429](D:/Projects/Аксико/app/src/main/java/app/assi/agent/Tools.kt:429).

**Предложение:** общий результат с ok, errorKind, exitCode, diagnostics, artifacts. Отдельно различать ошибку программы, неуспешную проверку, таймаут, недоступную возможность и временный сбой.

### 3. Нулевое или пропущенное покрытие может выглядеть зелёным

Воспроизведение текущего lib/check.js в памяти Node VM дало:

- пустой набор: «прошло 0 из 0»;
- единственный пропущенный сценарий: «прошло 1 из 1», затем строка «пропущено»;
- реальный assertion failure корректно помечается как провал.

Текущая selfChecks определяет успех отсутствием текста «НЕ ПРОШЛО», поэтому первые два случая проходят. Отсутствующий checks.js вообще исключается из списка автопроверок.

Основание: [lib/check.js:90](D:/Projects/Аксико/app/src/main/assets/factory/lib/check.js:90), [lib/check.js:105](D:/Projects/Аксико/app/src/main/assets/factory/lib/check.js:105), [Conversation.kt:708](D:/Projects/Аксико/app/src/main/java/app/assi/agent/Conversation.kt:708).

**Предложение:** структурированные passed/failed/skipped/missing/timedOut; обязательный минимальный набор сценариев для типа изменения. Пропуск должен объяснять, что именно осталось непроверенным. Проверки автора дополнить независимыми проверками общего контракта модуля и поведения UI.

### 4. Изменённая библиотека может остаться старой в уже загруженном модуле

Загрузчик require проверяет время изменения только самого файла. Если main.js сохранил объект из logic.js, замена logic.js не обновляет объект, который уже находится внутри main.js.

На точном коде загрузчика в Node VM воспроизведено: до изменения результат 1; после изменения дочернего файла повторный require(parent) всё ещё даёт 1; прямой require(child) уже даёт 2.

Основание: [bootstrap.js:109](D:/Projects/Аксико/app/src/main/assets/engine/bootstrap.js:109).

**Предложение:** учитывать граф зависимостей и инвалидировать зависимых потребителей. Добавить управляемые dispose/reload/start для модулей, чтобы при обновлении не оставались старые подписки, таймеры и объекты. Проверки должны фиксировать, какую ревизию они действительно исполняли.

Сетевые ошибки завершают ход, отдельного прикладного backoff для 429/5xx нет. Истории дочерних lasting=false разговоров не сохраняются как самостоятельные рабочие процессы.

## Порядок реализации

1. Структурировать результаты инструментов и проверок; исправить статусы завершения. Без этого остальные автоматические решения опираются на ненадёжные признаки.
2. Сделать проверку условием завершения и добавить ограниченный цикл исправления до финального ответа.
3. Исправить загрузку зависимостей и перенос контекста черновика; обеспечить тестовые данные и корректный откат.
4. Ввести независимую UI-проверку телефона и web с измеримыми критериями.
5. Добавить восстановление задач и сбор ошибок после публикации, связанных с конкретной ревизией.
6. Настроить поведение автономности и подбор инструментов/модели под задачу.

Изменения Conversation, Tools, Drafts, Workspace и загрузки упакованного runtime потребуют обновления APK. Проверки, шаблоны, инструкции и большая часть HTML-инструментов затем могут развиваться в workspace.

## Как измерить реальную самостоятельность

Нужен набор одинаково проверяемых задач и несколько запусков каждой с выбранной моделью:

| Сценарий | Независимый критерий успеха |
|---|---|
| Добавить небольшой модуль | Создание/изменение/удаление записи работает после перезапуска |
| Исправить синтаксическую ошибку | Проверка сначала красная, агент получает её и доводит до зелёного |
| Исправить раскладку вкладок | Одна прокручиваемая строка на узком экране, последний пункт доступен |
| Ускорить каталог | Порог времени до полезных карточек соблюдён на полном наборе игр |
| Изменить общую библиотеку | Использующие её модули выполняют именно новую ревизию |
| Мигрировать данные | Старые записи читаются, изменение обратимо в предусмотренных границах |
| Параллельно работать в draft | Рабочая версия не меняется до применения, конфликты обнаруживаются |
| Пережить обрыв сети/перезапуск | Задача продолжается, завершённое действие не повторяется |
| Сделать desktop UI | Проверен browser viewport, а не только телефон |

Для каждого запуска фиксировать успешность независимых сценариев, число вмешательств человека, время, стоимость, число попыток исправления и сохранность данных. Подставная модель полезна для проверки механизма цикла; качество самостоятельного решения измеряется настоящей моделью.

Предлагаемый критерий готовности первой версии: агент получает воспроизводимую ошибку проверки и сам доводит изолированную доработку до рабочего результата, подтверждённого повторной проверкой, без сообщения «готово» до её завершения.
